# Changelog

## 1.4.0 - 2026-08-27

Re-probed every documented endpoint live and asserted on the response BODY, not the status code. The headline finding reverses a rule the skill has carried for two cycles: **`datastore_search_sql` is NOT disabled.** `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, `sum()` and `LIMIT` all return HTTP 200 with `success:true` and real rows. What the WAF actually blocks is a small set of injection-signature substrings (`count(`, `1=1`, `UNION` all confirmed), and it answers with an **HTML 404 page of about 1.4 kB**, not a JSON error and not the 403 `Security Violation` the skill described. That 403 could not be reproduced at all this cycle. Two consequences now documented: use `sum(1)` where `count(*)` is blocked (verified to return the same aggregate), and use `WHERE _id > N ORDER BY _id` for true keyset paging, which `filters` still cannot do and which deep `offset` cannot match for speed.

Corrected the rate-limiting claim, which said gov.il rate limiting is "strict" and that rapid callers "will be blocked". 25 rapid sequential calls in 6.5 seconds all returned 200, and about 60 calls in one session drew no throttling. The Gotcha now states the measurement and warns against diagnosing a user's problem as rate limiting without evidence.

Fixed a broken link that sent users to a 404: the dataset list is at `https://data.gov.il/datasets` (plural). The singular `/dataset` renders a client-side error page, which is why a status check alone never caught it.

Two script bugs. `orgs` printed the slug twice and "(0 datasets)" for every organization, because data.gov.il returns `title` and `resources_count` rather than CKAN's `display_name` and `package_count` (both come back null); it now prints the Hebrew ministry names and real resource counts. And the script died with an opaque `Connection error: [SSL: CERTIFICATE_VERIFY_FAILED]` on a stock python.org macOS build; it now prefers certifi's bundle when installed and, failing that, prints the actual remedy instead of the raw error.

A second pass, prompted by an expert review, found that the endpoint layer was healthy while the DATA layer was quietly wrong, and fixed five paths that returned confident wrong answers to the skill's own worked examples:

- **CBS locality codes are space-padded text.** `filters={"סמל_ישוב":"4000"}` returns `success:true` with `total:0`; the stored value is `"4000 "`. A zero-row success is the most damaging thing this API produces, because the agent reports "no data" and nothing looks broken.
- **The documented name-join cannot match.** The same city is spelled three ways across the two resources the skill tells you to join.
- **The mosdot resource is a 2011-2015 per-year panel.** Its 119,761 rows are five years of the same institutions, and Example 1's unfiltered result of 18,574 was being presented as a current Tel Aviv school count. Resource metadata says 2026 because that is when the FILE was republished.
- **Date columns are text in DD/MM/YYYY**, so the documented `sort=<date> desc` sorts by day-of-month and returns the wrong most-recent row.
- **Example 2 chased a dataset that does not exist.** Real-estate transactions, GTFS and most CBS series are not on data.gov.il at all; the example now teaches the agent to stop and redirect rather than substitute a plausible dataset. A new "What is NOT on data.gov.il" table records where each actually lives.

One further WAF constraint surfaced while writing the fix, and it decides which tool to reach for: **SQL that references a Hebrew-named column in a predicate or a function is blocked** (`WHERE "שנה"=2015` and `WHERE TRIM("סמל_ישוב")='4000'` both return the HTML 404), while `SELECT`, `GROUP BY` and `ORDER BY to_date(...)` on the same Hebrew columns work, as does `WHERE` on a Latin column or on `_id`. So Hebrew-column filtering belongs to `datastore_search`'s `filters`, and SQL owns keyset paging, aggregation and date ordering. The first draft of the corrected Example 1 shipped a SQL year-filter that this rule blocks; it was caught by running the command rather than reasoning about it, and replaced with a `filters` call verified to return 26,239.

Troubleshooting was re-keyed on what the API actually returns (JSON 409 with a Hebrew `Validation Error`, JSON `success:true` with `total:0`, the shared 1,376-byte HTML 404) instead of invented English error strings, and the HTML-404 row now names all three of its causes rather than blaming the WAF for every one. The script gained a `sql` subcommand, `--records-format`, and `--json` for chaining, stopped suppressing `_id` (which keyset paging needs), prints the header ahead of headerless CSV output, and explains the HTML 404 rather than reporting `HTTP error 404: Not Found`.

Re-verified against the live API: all four resource IDs resolve with bodies (counts refreshed to their exact values 4,168,353 / 65,953 / 119,761 / 75,680), all seven organization IDs return non-zero package counts, the CBS locality codes 5000 / 4000 / 3000 match the localities resource, the mosdot `שם ישוב` and localities `סמל_ישוב` field names are correct, `fields` / `sort` / `offset` / `q` / `filters` / `records_format` were each confirmed to CHANGE the result rather than being silently ignored, `offset=500000` still returns data, and `filters={"_id":">N"}` still fails with `success:false`. A negative control (an undefined sibling action, and a bogus resource id) returns 404 HTML, confirming the API discriminates rather than answering everything with 200.

All notable changes to this skill are documented here.
