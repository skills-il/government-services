# ממשקי API ממשלתיים - ישראל

## הוראות

### שלב 1: תבינו מה המשתמש צריך
תשאלו את המשתמש:
- **באיזה נושא?** (תחבורה, בריאות, חינוך, כלכלה וכו')
- **באיזה אזור?** (ארצי, עיר או אזור ספציפי, כתובת מסוימת)
- **באיזו תקופה?** (עכשיו, היסטורי, סדרה לאורך זמן)
- **באיזה פורמט?** (נתונים גולמיים, סטטיסטיקה מסכמת, ויזואליזציה)

### שלב 2: חיפוש datasets
תשתמשו ב-API של data.gov.il (מבוסס CKAN) כדי למצוא datasets רלוונטיים:

**חיפוש לפי מילת מפתח:**
```
GET https://data.gov.il/api/3/action/package_search?q=KEYWORD&rows=10
```

**חיפוש לפי ארגון (משרד ממשלתי):**
```
GET https://data.gov.il/api/3/action/package_search?fq=organization:MINISTRY_ID
```

**מזהי ארגונים נפוצים:**
| משרד | מזהה | שם באנגלית |
|------|------|------------|

| משרד התחבורה | ministry_of_transport | Ministry of Transportation |
| משרד הבריאות | ministry-health | Ministry of Health |
| משרד החינוך | ministry_of_education | Ministry of Education |

| רשות מקרקעי ישראל | the_israel_lands_administration | Israel Land Authority |

### שלב 3: שליפה ושאילתה
אחרי שמצאתם את ה-dataset:

**קבלת פרטי dataset:**
```
GET https://data.gov.il/api/3/action/package_show?id=DATASET_ID
```

**שאילתה על נתונים טבלאיים (datastore):**
```
GET https://data.gov.il/api/3/action/datastore_search?resource_id=RESOURCE_ID&limit=100
```

**סינון לפי ערכי שדות:**
```
GET https://data.gov.il/api/3/action/datastore_search?resource_id=RESOURCE_ID&filters={"field_name":"value"}&limit=100
```

**בחירת שדות ספציפיים ומיון:**
```
GET https://data.gov.il/api/3/action/datastore_search?resource_id=RESOURCE_ID&fields=field1,field2&sort=field1 desc&limit=100
```

**חיפוש טקסט חופשי במשאב:**
```
GET https://data.gov.il/api/3/action/datastore_search?resource_id=RESOURCE_ID&q=search+term&limit=100
```

**`datastore_search_sql` עובד, עם חור אחד בצורת WAF.** נבדק מחדש חי ב-27/8/2026: `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, `sum()` ו-`LIMIT` כולם מחזירים HTTP 200 עם `success:true` ושורות אמיתיות. מה שה-WAF חוסם זה קבוצה קטנה של מחרוזות שנראות כמו הזרקת SQL, ובהן `count(`, `1=1` ו-`UNION`, והוא עושה את זה עם **עמוד HTML של 404, לא שגיאת JSON ולא 403**, כך שלקוח שבודק רק את `success` יקרא את החסימה כשגיאת פענוח.

- תשתמשו ב-`sum(1)` במקום ב-`count(*)`. השאילתה `SELECT col, sum(1) AS n FROM "<resource_id>" GROUP BY col ORDER BY n DESC LIMIT 10` מחזירה בדיוק את מה שצורת ה-`count(*)` החסומה הייתה מחזירה.
- לספירת שורות פשוטה בכלל לא צריך SQL: השדה `total` של `datastore_search` כבר מכיל אותה.
- **SQL הוא הדרך היחידה לקבל keyset paging אמיתי.** `filters` לא יכול, אבל `SELECT ... FROM "<rid>" WHERE _id > <last_id> ORDER BY _id LIMIT <n>` עובד ונשאר מהיר בכל עומק, בניגוד ל-offset עמוק.
- **תקראו את **צורת** התגובה לפני שאתם מאבחנים משהו.** data.gov.il עונה על שני סוגי הכשל בצורה שונה לגמרי, וערבוב ביניהם שולח את הסוכן לתיקון הלא נכון:
  - **JSON עם HTTP 409** והודעת `psycopg2` פירושו שה-SQL שלכם הגיע ל-Postgres ו-Postgres דחה אותו (עמודה לא קיימת, תחביר שגוי, טבלה לא קיימת). תקראו את ההודעה ותתקנו את השאילתה.
  - **עמוד HTML עם HTTP 404** בגודל כ-1.4 קילובייט פירושו שהבקשה בכלל לא הגיעה לשכבת ה-SQL. זה עמוד השגיאה **הגנרי** של האתר, ויש לו לפחות שלוש סיבות שונות: מחרוזת שה-WAF זיהה, שם action שלא קיים, ו-resource_id שלא קיים. אל תניחו שזה ה-WAF. תבדילו ביניהן בהרצה חוזרת של שאילתה ידועה כתקינה (`SELECT * FROM "<rid>" LIMIT 1`) על אותו משאב: אם היא מצליחה, המשאב תקין וה-SQL שלכם הפעיל את ה-WAF; אם גם היא מחזירה HTML, ה-resource_id מת או שם ה-action שגוי.

**טיפים:**
- שמות השדות בדרך כלל בעברית, תריצו `datastore_search` עם `limit=1` קודם כדי לראות את שמות השדות
- הפרמטר `filters` מקבל אובייקט JSON להתאמה מדויקת (למשל `filters={"city_code":"5000"}`)
- הפרמטר `q` לחיפוש טקסט חופשי בכל השדות
- ל-datasets גדולים, תשתמשו ב-`limit` ו-`offset` לדפדוף
- שדות תאריך מגיעים בפורמטים שונים, תבדקו את תיעוד ה-dataset

**דפדוף (pagination):**
- דפדוף offset עמוק נעשה איטי וכבד יותר ככל שמתקדמים ב-datasets גדולים. אין תקרה קשיחה (offset גבוה עדיין מחזיר נתונים), אבל העלות גדלה עם ה-offset.
- דפדפו עם `limit` + `offset`: התגובה מחזירה `_links.next` (כתובת הדף הבא מבוססת offset) שאפשר לעקוב אחריה, או להגדיל `offset` ידנית. ה-`filters` של data.gov.il עושה התאמה מדויקת בלבד, ולכן אין keyset paging על `_id` **דרך `filters`**: `filters={"_id":">N"}` מחזיר `success:false`. לעומת זאת `datastore_search_sql` עם `WHERE _id > N ORDER BY _id` כן נותן keyset paging אמיתי (ראו שלב 3).
- לשליפות גדולות מאוד או של טבלה שלמה, השתמשו ב-`records_format=csv` או הורידו את קובץ המשאב מ-`resources[].url` ב-`package_show`. שימו לב שקובץ המשאב הוא לא פעם **XLSX ולא CSV** (כך למשל במשאב mosdot), ולכן `records_format=csv` הוא הנתיב האמין ל-CSV; תבדקו את `resources[].format` לפני שאתם מניחים.
- השדה `total` בתגובה הוא ספירה של כל הרשומות במשאב (לא רק בדף), השתמשו בו לתכנון מספר הדפים.
- הפרמטר `records_format` מקבל את הערכים `objects` (ברירת מחדל), `lists` (מערכים לפי מיקום), `csv` ו-`tsv`. `lists` ו-`csv` מהירים וזולים בהרבה לשליפות גדולות, כדאי בסטרימינג או חילוץ בכמויות.

### שלב 3ב': מלכודות בשכבת הנתונים (תקראו לפני שאתם מצטטים מספר)

שלב 3 מביא לכם 200 עם שורות. אלה הדרכים שבהן השורות האלה עדיין שגויות. כל אחת מהן שוחזרה מול ה-API החי ב-27/8/2026.

**עמודות טקסט מרופדות ברווח, וקודים שנראים מספריים שמורים כטקסט.** במשאב היישובים של הלמ"ס, `סמל_ישוב` הוא מסוג `text` והערכים שלו נושאים **רווח בסוף**: `filters={"סמל_ישוב":"4000"}` מחזיר `success:true` עם `total:0`, ואילו `"4000 "` מחזיר את חיפה. תשובה מוצלחת עם אפס שורות היא התשובה השגויה השקטה הנפוצה ביותר של ה-API הזה, כי הסוכן מדווח "אין נתונים" ושום דבר לא נראה שבור. תמיד תבדקו את הערך הגולמי עם `limit=1` לפני סינון שוויון על שדה טקסט, ואז תתאימו ל**מחרוזת המרופדת המדויקת** דרך `filters` (`{"סמל_ישוב":"4000 "}` עובד), או תיפלו חזרה ל-`q=` חיפוש חופשי. אי אפשר לפתור את זה עם TRIM ב-SQL, מהסיבה שבפסקה הבאה.

**ה-WAF חוסם גם SQL שמתייחס לעמודה בעלת שם עברי בתנאי או בפונקציה.** זו האילוצה הכי מפתיעה ב-API והיא קובעת באיזה כלי משתמשים. אומת ב-27/8/2026:

| SQL | תוצאה |
|---|---|
| `SELECT "שנה" FROM "<rid>" LIMIT 1` | 200, עובד |
| `... GROUP BY "שנה"` | 200, עובד |
| `... ORDER BY to_date("תאריך רישום עמותה",'DD/MM/YYYY') DESC` | 200, עובד, וזה התיקון הנכון לתאריכי טקסט |
| `... WHERE "שנה" = 2015` | HTML 404, חסום |
| `... WHERE TRIM("סמל_ישוב") = '4000'` | HTML 404, חסום |
| `... WHERE shnat_yitzur = 2016` (עמודה לטינית) | 200, עובד |
| `... WHERE _id > 100` | 200, עובד |

חלוקת העבודה היא: **לסנן עמודות עבריות עם `filters` של `datastore_search`** (שמטפל בערכים בעברית מצוין, בכפוף לכלל הרווח בסוף שלמעלה), ו**להשתמש ב-SQL ל-keyset paging על `_id`, לתנאים על עמודות לטיניות, ל-`GROUP BY`, ל-`sum(1)` ולסידור עם `to_date`**. אל תנסו לעשות TRIM לעמודה עברית ב-SQL, תתאימו במקום זה למחרוזת המרופדת המדויקת דרך `filters`.

**join לפי שם יישוב לא עובד בלי נרמול.** אותה עיר מאויתת בשלוש צורות בין שני המשאבים שהסקיל אומר לחבר: היישובים מחזיק `'תל אביב - יפו '` (עם רווח בסוף), המוסדות מחזיק `'תל אביב - יפו'` ב-`שם ישוב` ו-`'תל אביב-יפו'` ב-`שם רשות`. join תמים על שוויון מוחק כל שורה. תשלפו את שני הצדדים ותנרמלו בקוד שלכם (strip, ואז איחוד הרווחים סביב המקף); אי אפשר לדחוף את הנרמול לתוך ה-SQL, כי פונקציה על עמודה עברית חסומה.

**חלק מהמשאבים הם פאנל רב-שנתי, וספירת השורות הראשית שלהם היא לא ספירה של דברים.** משאב המוסדות מחזיק שורה אחת למוסד **לכל שנה**, ורק לשנים **2011 עד 2015**, כך ש-119,761 השורות שלו הן חמש שנים של אותם מוסדות ואין בו שום דבר אחרי 2015. תסננו לפי `שנה` לפני שאתם סופרים משהו, ולעולם אל תציגו את סך המשאב בתור "מספר בתי הספר".

**טריות המטא-דאטה של המשאב אינה טריות הנתונים.** `resource_show` על המוסדות מדווח `last_modified` של 2026, שמתאר מתי ה**קובץ** פורסם מחדש, בזמן שהנתונים בפנים נגמרים ב-2015. תגזרו את שנת הנתונים מעמודת התאריך של הנתונים עצמם לפני שאתם מצטטים מספר למשתמש.

**עמודות תאריך הן טקסט, ולכן `sort` עליהן הוא לקסיקוגרפי ושגוי.** במשאב העמותות גם `תאריך רישום עמותה` וגם `תאריך עדכון סטטוס` הם מסוג `text` בפורמט DD/MM/YYYY, כך ש-`sort=תאריך רישום עמותה desc` מציב את `31/12/2025` מעל כל שורה מינואר 2026: הוא ממיין קודם לפי היום בחודש. הפורמטים גם משתנים בין עמודות של אותו משאב. לסדר כרונולוגי אמיתי תשתמשו ב-SQL: `ORDER BY to_date("תאריך רישום עמותה",'DD/MM/YYYY') DESC` מחזיר 26/08/2026 בראש, אומת ב-27/8/2026. `to_date` ב-ORDER BY מותר גם על עמודה עברית; רק תנאים ו-TRIM חסומים.

**`records_format=csv` מחזיר מחרוזת CSV בלי שורת כותרות.** שמות העמודות קיימים רק ב-`result.fields`, לפי הסדר. תוסיפו אותם בעצמכם, אחרת העמודות בעברית יזוזו בשקט.

**תבדקו `datastore_active` לפני שאילתה.** `package_show` ו-`resource_show` חושפים אותו לכל משאב, והוא בלתי תלוי ב-`format`: משאב המוסדות הוא `XLSX` ועדיין `datastore_active:true`. משאב עם `datastore_active:false` חייב הורדה מ-`resources[].url` ופענוח מקומי.

### שלב 4: ניתוח והצגה
אחרי שיש לכם את הנתונים:
1. תסכמו את הממצאים העיקריים בשפה פשוטה
2. תחשבו סטטיסטיקות בסיסיות אם צריך (ממוצע, חציון, מגמות)
3. תציעו ויזואליזציות (תרשים עמודות, גרף קווי, מפה) שמתאימות לנתונים
4. תציינו את תאריך העדכון האחרון וכל הסתייגות רלוונטית
5. תספקו קישור ישיר ל-dataset ב-data.gov.il

### שלב 5: הצלבת נתונים (מתקדם)
כשמשלבים כמה datasets:
1. תזהו מפתחות משותפים (קוד יישוב, תאריך, קוד קטגוריה)
2. תשתמשו בקודים מנהליים ישראליים (קודי יישוב של הלמ"ס) לחיבור גיאוגרפי
3. שימו לב ששמות שדות בין datasets שונים לא תמיד זהים, תתאימו לפי תוכן ולא לפי שם
4. תתעדו את מקור הנתונים: אילו datasets תרמו לניתוח

הארגון `lamas` ב-CKAN הוא פרוסה קטנה מהתפוקה של הלמ"ס. אל תבטיחו למשתמש סדרה של הלמ"ס בלי לבדוק שהסדרה הספציפית הזאת נמצאת בפורטל.

## דוגמאות

### דוגמה 1: חיפוש נתוני בתי ספר (workflow מלא עם שרשור קריאות)
המשתמש אומר: "אני צריך נתונים על בתי ספר בתל אביב"

פעולות (אל תדלגו על שלבי האיתור, מזהי משאבים מתחלפים):

1. חיפוש datasets רלוונטיים:
   ```
   curl -s "https://data.gov.il/api/3/action/package_search?q=mosdot&rows=5"
   ```
2. בדיקת ה-dataset שנבחר ושליפת `resources[].id` הפעיל:
   ```
   curl -s "https://data.gov.il/api/3/action/package_show?id=mosdot" \
     | python3 -c "import sys,json; r=json.load(sys.stdin)['result']['resources']; [print(x['id'], x['format'], x.get('name','')) for x in r]"
   ```
3. הצצה לשמות שדות עם `limit=1`:
   ```
   curl -s "https://data.gov.il/api/3/action/datastore_search?resource_id=5548fd63-5868-4053-ad81-98caddc5e232&limit=1"
   ```
4. משאב המוסדות חושף את היישוב כשדה שם `שם ישוב` (טקסט שם היישוב, למשל `תל אביב - יפו`), לא כקוד מספרי. סננו לפי שם היישוב (או השתמשו ב-`q=` לחיפוש חופשי); עברית חייבת להיות מקודדת ב-percent-encoding:
   ```
   # חיפוש חופשי למוסדות בתל אביב (q = "תל אביב", מקודד)
   curl -s "https://data.gov.il/api/3/action/datastore_search?resource_id=5548fd63-5868-4053-ad81-98caddc5e232&q=%D7%AA%D7%9C%20%D7%90%D7%91%D7%99%D7%91&limit=100"
   ```
   קוד היישוב המספרי של הלמ"ס (תל אביב-יפו 5000, חיפה 4000, ירושלים 3000) הוא השדה `סמל_ישוב`, אבל הוא נמצא ב-dataset היישובים של הלמ"ס (משאב `5c78e9fa-c2e2-4771-93ff-7f400a12f7ba`), לא במשאב המוסדות. הערכים שלו הם **טקסט מרופד ברווח**, אז תתאימו עם `TRIM(...)`, ותנרמלו את שם העיר לפני כל join (ראו שלב 3ב').
5. **תבחרו שנה, אחרת התשובה היא חמש שנים של כפילויות.** משאב המוסדות הוא פאנל שנתי שמכסה רק 2011 עד 2015, ולכן התוצאה הלא מסוננת של `q=תל אביב` שעומדת על 18,574 אינה ספירת בתי ספר. `שנה` היא עמודה בשם עברי, אז תסננו אותה דרך `datastore_search` ולא דרך SQL (WHERE על עמודה עברית חסום ב-WAF, ראו שלב 3ב'): `filters={"שנה":"2015"}`, ותקראו את `total` מהתשובה. הפילוח השנתי עצמו כן חוקי ב-SQL, כי `GROUP BY` על עמודה עברית מותר: `SELECT "שנה", sum(1) AS n FROM "<rid>" GROUP BY "שנה"`.

תוצאה: רשימת בתי ספר מובנית עבור תל אביב (מספר, סוגים, גדלים).

### דוגמה 2: בקשה שהקטלוג לא יכול לשרת
המשתמש אומר: "הראה לי מגמות מחירי דיור בחיפה"

פעולות:
1. `package_search?q=nadlan` או `q=%D7%A2%D7%A1%D7%A7%D7%90%D7%95%D7%AA` כדי לאתר את ה-dataset של עסקאות נדל"ן ברשות המסים.
2. `package_show?id=<slug>` ושליפת מזהה המשאב של השנה העדכנית מתוך `resources[]`.
3. `datastore_search` עם סינון לקוד יישוב חיפה, מסודר לפי תאריך עסקה יורד.
4. קיבוץ לפי חודש, חישוב מחיר חציוני למטר רבוע, חישוב אחוז שינוי חודש מול חודש קודם.

תוצאה: מגמת מחירים חודשית לחיפה עם ניתוח.

### דוגמה 3: השוואת נתונים מוניציפליים
המשתמש אומר: "תשווי לי הוצאות חינוך בין ערים בישראל"

פעולות:
1. `package_search?q=%D7%AA%D7%A7%D7%A6%D7%99%D7%91%20%D7%97%D7%99%D7%A0%D7%95%D7%9A` (תקציב + חינוך בעברית, מקודד).
2. בחירת dataset של תקציבים מוניציפליים, `package_show` כדי לקבל את מזהה המשאב הפעיל.
3. `datastore_search` עם סינון לשורות בקטגוריית חינוך; דפדוף עם offset (או הורדת ה-CSV של המשאב) למשאבים גדולים.
4. נרמול לנפש בעזרת נתוני אוכלוסיה של `lamas` (למ"ס).

תוצאה: השוואה מדורגת של הוצאות חינוך לתלמיד בין רשויות מקומיות גדולות, כולל מקור הנתונים והשנה.

## מלכודות נפוצות
- ממשקי API ממשלתיים (data.gov.il) משנים תדיר כתובות URL ומבני endpoints בלי התראה. סוכנים לפעמים מקודדים endpoints שעבדו בחודש שעבר אבל עכשיו מחזירים 404. תאמתו מזהי משאבים מחדש עם `package_show` לפני שאתם מצטטים אותם.
- ה-API של data.gov.il מחזיר נתונים עם כותרות עמודות בעברית כברירת מחדל. סוכנים עלולים להיכשל בפענוח תגובות עם שמות לא-ASCII ב-JSON או CSV.
- ערכי סינון ופרמטרי `q` בעברית חייבים להיות מקודדים ב-UTF-8 percent-encoding. עברית גולמית ב-URL שוברת כמה לקוחות HTTP (חלק מהגרסאות של `curl`, גרסאות ישנות של `requests`, חלק מה-proxies). דוגמה: חיפוש "רכב" כ-`q=%D7%A8%D7%9B%D7%91`; סינון "חיפה" כ-`filters=%7B%22city%22%3A%22%D7%97%D7%99%D7%A4%D7%94%22%7D`.
- הגבלת הקצב לא מתועדת, וקל להגזים בחומרתה. **אומת ב-27/8/2026: 25 קריאות `datastore_search` רצופות ומהירות ב-6.5 שניות החזירו כולן 200, וכ-60 קריאות לאורך session אחד לא גררו ויסות בכלל.** תתייחסו להשהיה קטנה כאדיבות ולא כדרישה מתועדת, ואל תגידו למשתמש שהבעיה שלו היא הגבלת קצב בלי ראיות; החסימה שאנשים באמת נתקלים בה היא ה-WAF של תבניות ה-SQL שלמטה.
- ה-WAF של data.gov.il חוסם SQL שמתאים לחתימת הזרקה (`count(`, `1=1` ו-`UNION` אומתו ב-27/8/2026) ועונה ב**עמוד HTML של 404 בגודל כ-1.4 קילובייט**, לא ב-JSON ולא ב-403. כתיבה מחדש של השאילתה פותרת את זה מיד, ו-backoff לא, כי שום דבר לא מווסת. תשובת 403 עם הגוף `Security Violation` נצפתה ביוני 2026 אבל **לא** הצליחה להשתחזר ב-27/8/2026; אם בכל זאת נתקלתם באחת, תתייחסו אליה כחסימה ברמת ה-session (זריקת cookies, `User-Agent` חדש, backoff אקספוננציאלי) ולא כבעיה בשאילתה.
- הרבה datasets ממשלתיים שומרים תאריכים בפורמט DD/MM/YYYY (הפורמט הישראלי), לא ISO 8601. סוכנים עלולים לפענח "01/02/2026" כ-1 בפברואר במקום 2 בינואר.
- דפדוף offset עמוק נעשה איטי יותר ב-datasets גדולים (אומת ב-27/8/2026: `offset=500000` עדיין מחזיר 200, אז אין תקרה קשיחה, אבל offset גבוה יקר). ה-`filters` לא יכול לעשות keyset paging (`{"_id":">N"}` נכשל עם `success:false`), אבל `datastore_search_sql` עם `WHERE _id > N ORDER BY _id` כן יכול, וזה הכלי הנכון לשליפה מלאה.

## פתרון בעיות

### `package_search` מחזיר `count: 0`
סיבה: מונחי חיפוש ספציפיים מדי, או בשפה לא נכונה, או שהנתונים פשוט לא נמצאים בפורטל הזה.
פתרון: תנסו מילות מפתח רחבות יותר בעברית (רוב הקטלוג בעברית), ואז `fq=organization:<id>`. אם עדיין אפס, תבדקו את טבלת "מה לא נמצא ב-data.gov.il" בשלב 2 לפני שאתם מסיקים משהו: ספירת אפס לנדל"ן, ל-GTFS ולרוב סדרות הלמ"ס היא התשובה הנכונה והסופית, והמהלך הנכון הוא להפנות את המשתמש ולא להחליף ב-dataset אחר.

### JSON עם HTTP 409 ושגיאת `Validation Error` בעברית
סיבה: הבקשה הגיעה ל-CKAN ו-CKAN דחה את הארגומנטים. `resource_id` חסר, למשל, מחזיר `{"error":{"resource_id":["ערך חסר"],"__type":"Validation Error"},"success":false}` עם HTTP 409. ההודעה בעברית.
פתרון: תקראו את `error` ולא את הסטטוס. זו תקלה בצד הקורא ולא תקלה בשירות.

### למשאב אין datastore לשאילתות
סיבה: `datastore_active` הוא false למשאב הזה. הוא בלתי תלוי ב-`format`: משאב XLSX יכול להיות datastore-active (המוסדות הוא כזה), ומשאב CSV יכול לא להיות.
פתרון: תקראו את `resources[].datastore_active` מ-`package_show` או `resource_show` **לפני** קריאה ל-`datastore_search`. אם false, תורידו את `resources[].url` ותפענחו מקומית.

### שגיאה: עמוד HTML במקום JSON מ-`datastore_search_sql`
סיבה (אומתה ב-27/8/2026): הבקשה בכלל לא הגיעה לשכבת ה-SQL. עמוד ה-HTML של 404 בגודל 1,376 בתים הוא עמוד השגיאה **הגנרי** של האתר, ומשותף לשלוש סיבות: ה-WAF זיהה מחרוזת הזרקה ב-SQL שלכם (`count(`, `1=1` ו-`UNION` מפעילים אותו), או ששם ה-action לא קיים, או שה-resource_id לא קיים. בשלושת המקרים לקוח שבודק רק את `success` רואה שגיאת פענוח.
פתרון: קודם כול להבדיל. תריצו מחדש `SELECT * FROM "<resource_id>" LIMIT 1`. אם זה מצליח, ה-SQL שלכם הפעיל את ה-WAF: תחליפו `count(*)` ב-`sum(1)`, תיקחו ספירת שורות מהשדה `total` של `datastore_search`, ותימנעו מ-`UNION` ומטאוטולוגיות. אם גם זה מחזיר HTML, ה-resource_id מת (תפתרו אותו מחדש עם `package_show`) או ששם ה-action שגוי. ה-endpoint עצמו **אינו** מושבת.
מה שנבדק ואינו הסיבה: הגבלת קצב (25 קריאות מהירות ב-6.5 שניות החזירו כולן 200), ושגיאת SQL אמיתית, שמחזירה **JSON עם HTTP 409** והודעת `psycopg2` ולא HTML.

### שגיאה: `Connection error: [SSL: CERTIFICATE_VERIFY_FAILED]` מהסקריפט המצורף
סיבה: התקנת python.org ב-macOS מגיעה בלי מאגר תעודות מאוכלס, ולכן `urllib` לא מצליח לאמת את התעודה של data.gov.il. זו בעיית אמון מקומית ולא תקלה של data.gov.il; `curl` על אותה מכונה עובד.
פתרון: הסקריפט מעדיף עכשיו את חבילת התעודות של `certifi` כשהיא מותקנת (`pip install certifi`). לחלופין הריצו פעם אחת את `Install Certificates.command` שמגיע עם python.org, או הגדירו `SSL_CERT_FILE=$(python3 -c 'import certifi; print(certifi.where())')`.

### `success:true` עם `total: 0` כשברור שהנתונים קיימים
סיבה (אומתה ב-27/8/2026): כמעט תמיד עמודת טקסט מרופדת ברווח. `filters={"סמל_ישוב":"4000"}` על משאב היישובים מחזיר אפס שורות כי הערך השמור הוא `"4000 "`. קודים שנראים מספריים שמורים כ-`text`, ולכן גם `"4000"` ו-`4000` שונים.
פתרון: תבדקו קודם את הערך הגולמי עם `limit=1`, ואז או תתאימו למחרוזת המרופדת המדויקת או תשתמשו ב-`datastore_search_sql` עם `WHERE TRIM("col") = 'value'`. ראו שלב 3ב'.

### שמות שדות בעברית
זו לא שגיאה. לרוב ה-datasets יש שמות עמודות בעברית, לפעמים עם רווח (`שם ישוב`) ולפעמים עם קו תחתון (`שם_ישוב`) במשאבים שונים. תריצו `limit=1` קודם כדי לקרוא את שמות השדות המדויקים, ותקודדו אותם ב-URL.
